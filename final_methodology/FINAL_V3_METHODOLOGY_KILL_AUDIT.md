# Final V3 methodology kill audit

This audit tests whether the bounded V2 paper survives the strongest methodology objections and whether the requested V3 hardening is complete. V2 evidence is not rewritten.

| Attack | Severity | Finding | Repair/status | Residual risk |
|---|---|---|---|---|
| The work is conversion inspection, not software testing | HIGH | The testing contribution is defensible only when contracts, fixtures, pipelines-as-SUT, destination evidence, differential comparison, and abstaining oracle decisions are explicit. | Added a formal V3 decision spec, machine-readable rules, precedence tests, label-blinded reclassification, calibration reports, and oracle spec. | No general testing theory is claimed; an ICST reviewer may still prefer a broader software fault model. |
| Novelty is swallowed by DocAccessible/DAISY and prior conversion work | HIGH | Broad “first” or “no prior work” novelty is untenable. Current DocAccessible materials describe evidence-traceable conversion benchmarks; DAISY reports a 2026 conversion benchmark. | Added current prior-art recheck and narrowed distinction to source-grounded DOCX-to-PDF preservation contracts and uncertainty-aware cross-format evidence. | The contribution may be judged incremental or too domain-specific. |
| One atomic instance per feature is a smoke-test suite | HIGH | Valid criticism of external validity and within-feature coverage, not proof that the bounded protocol is invalid. | Added explicit coverage matrix, Variant Set B design, and limitation that the suite is purposive, not exhaustive. | No formal test-adequacy criterion | HIGH | There is a documented purposive selection basis but no formal adequacy metric or standards-completeness claim. | Added feature coverage/adequacy boundary grounded in machine representability, accessibility relevance, conversion relevance, and inspectability. | A reviewer can still request coverage criteria or mutation testing; that would be future work, not a factual repair. |

## Most plausible rejection arguments

1. The contribution is too close to existing document-conversion benchmarking and too narrow for a software-testing venue.
2. Six unresolved cases and two calibration false negatives make the cross-format oracle too incomplete for strong conformance claims.
3. One fixture per feature family is a handcrafted probe set without a formal adequacy criterion.
4. The two-pipeline result and Google cloud condition are too small and unstable for broader conclusions.
5. The V3 methodology extension is incomplete because Google repeatability and variant outputs could not be collected.

None of these invalidates the bounded V2 question, but #5 prevents claiming a completed V3 robustness study. The paper must be framed as a controlled protocol/benchmark, not as a general converter evaluation or completed reliability study.
